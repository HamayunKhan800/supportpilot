# M8 · Deployment and live demo: plan

> Status: **draft, waiting for owner approval** · 2026-10-25 · No application code or cloud resources until approved.
> Owner decisions so far: Google Cloud Run (option A), own domain, real Gemini on the free tier.

## Goal

A live, always-reachable demo on the owner's domain, deployed by GitHub Actions from `main`, with a staging copy checked before every production release, and the M8 items left over from earlier milestones closed or written down.

**Exit criteria (all verified, not assumed):**

1. `https://<domain>` serves the app over HTTPS with a public certificate; the demo accounts sign in; the portal accepts a request; Gemini triages it and drafts a cited reply.
2. A push to `main` builds one image, deploys it to staging, migrates, smoke-tests, then waits for the owner's approval before production. A bad release can be rolled back to the previous revision in one command, and that has been tried once.
3. No long-lived cloud keys anywhere: GitHub signs in to Google with Workload Identity Federation; app secrets live in Secret Manager.
4. A budget alert and a spend cap exist, and the expected monthly cost is shown against the real bill after one week.
5. Real email (password reset, verification code) works from the domain, with SPF, DKIM and DMARC passing.
6. The 10 ASVS items marked "M8" and the M8 notes in `accepted-risks.md` are each checked on the live site and given a verdict.

## Code changes (small; each with tests)

1. **Container launcher** (`scripts/start-container.mjs`, copied into the image): starts `server.js` and `.build/worker.mjs`, passes `SIGTERM` to both, and exits if either stops so Cloud Run restarts the instance. The default `CMD` for other platforms stays `node server.js`.
2. **Demo safety.** Visitors share the demo accounts, so:
   - the demo accounts can't change their password, name or email, or remove members (refused on the server, with a clear message);
   - no email is ever sent to a demo address, and the demo addresses move to the owner's domain (today they use `demo.supportpilot.dev`, a domain we don't own: a reset email there could reach a stranger once email is live);
   - a scheduled GitHub Action resets the demo workspace once a day (runs `seed-demo` as a Cloud Run job, bundled into the image with a new `--reset` mode).
3. **One address only:** in production, requests to the `*.run.app` address redirect to `<domain>` (the run.app URL can't be switched off while domain mapping is used).
4. **Daily embedding cap for the demo** (M4 note): search and upload embeddings get a daily limit, like generation already has.
5. **TRACE** (M7-11): checked on the live site first. Google's front end may already refuse it; if not, the launcher answers 405 before Next.js.

No table changes. No new runtime dependencies.

## Risks and limits (honest list)

- **First visit after a quiet spell is slower** (the app and the database wake up). Measured in step 6; if it is more than a few seconds, the options are one warm instance in working hours (a small cost) or accepting it.
- **Domain mapping is Preview** (AR-009). If it misbehaves, the fix is the load balancer (about $18 a month), with your approval.
- **Free plans change.** Every limit above is re-checked on the official pages before step 3, and the week-1 bill is compared with this plan.
- **Shared demo accounts** can still be used to make a mess between daily resets; anything harmful is blocked, the rest is reset.
- **Gemini free tier**: Google may use inputs to improve its products, so the demo stays on synthetic data, and the sign-up page says so.

## Not in M8

Multi-region, a paid database, CDN or Cloud Armor, two-factor sign-in (AR-007), a status page, load testing beyond a short smoke test.
