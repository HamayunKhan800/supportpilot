# M4 · Knowledge base: implementation plan

> Status: **Approved 2026-10-22** · Drafted 2026-10-22
> Implements FR-K1–K4 (docs/01 §3), NFR-SEC1/SEC2/SEC3/A11Y1/RESP1/REL2/OBS1/PRIV1, and threats T1, T9 (provenance part), T11, T12, T14, T16, T17 (docs/03).
> Roadmap row (docs/00): "Upload → worker → chunk → embed → HNSW index; retrieval API". Done when: ingestion integration tests pass and a retrieval recall baseline is recorded.
> No text generation in this milestone. M4 builds the **retrieval** that M5's cited drafts will use. The only AI call is the embedding model.

## 1. What a user can do when M4 is done

**Admin / owner** (signed in), on a new **Knowledge** page `/app/knowledge`:

1. **Upload** a `.md`, `.txt` or `.pdf` help article (≤ 5 MB, PDF ≤ 50 pages).
2. Watch its **status** change on its own: `pending → processing → ready`, or `failed` with a plain reason ("PDF has more than 50 pages", "no extractable text, scanned PDFs are not supported", "embedding service unavailable, try again").
3. **Retry** a failed document, or **delete** a document. Its passages disappear from search immediately.
4. Open a document to see **how it was split** into passages (heading path and text of each chunk).
5. Use the **test search** box. Type a customer-style question and see the top 5 passages, with their scores and whether keyword search, meaning-based search or both found them (FR-K4).

**Agent:** sees the document list and document pages (read-only). No upload, delete or test search (docs/01 §2.1 role matrix).

**Behind the scenes:** a separate **worker** process does the slow work (extract text → split → embed → store). The web server never parses an uploaded PDF.

## 2. Design decisions

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | **Embedding model `gemini-embedding-2`**, called through the Vercel AI SDK (`@ai-sdk/google`, ADR-0006). Not `gemini-embedding-001`.                                                                                                                                                                                                                                                                                                                                                                                                                                    | Google's deprecations page lists `gemini-embedding-001` for shutdown on **2028-05-14**, with `gemini-embedding-2` as the replacement; the newer model has no shutdown date ([deprecations](https://ai.google.dev/gemini-api/docs/deprecations)). It accepts 8,192 input tokens vs 2,048 ([embeddings](https://ai.google.dev/gemini-api/docs/embeddings)). Text input is **free on the free tier** ($0.20 per 1M tokens on paid) ([pricing](https://ai.google.dev/gemini-api/docs/pricing)).       |
| D2  | **768 dimensions**, column `embedding vector(768)`, **HNSW** index with `vector_cosine_ops`. If the recall target (≥ 90%) is missed at 768, the step-6 experiment also tries 1536.                                                                                                                                                                                                                                                                                                                                                                                      | Google recommends 768, 1536 or 3072, "sacrificing little in terms of quality" at smaller sizes ([embeddings](https://ai.google.dev/gemini-api/docs/embeddings)). pgvector's HNSW index caps `vector` at **2,000 dimensions**, so 3072 cannot be indexed as `vector` ([pgvector](https://github.com/pgvector/pgvector)). 768 floats = ~3 KB per chunk, which suits the free database tier.                                                                                                         |
| D3  | **Task prefixes exactly as Google documents them.** Chunks are embedded as `title: {document title} \| text: {chunk}`. Queries are embedded as `task: search result \| query: {question}`.                                                                                                                                                                                                                                                                                                                                                                              | `gemini-embedding-2` has no `task_type` setting. Google "strongly recommend[s]" these prefixes for retrieval ([embeddings §Task types with Embeddings 2](https://ai.google.dev/gemini-api/docs/embeddings)). Unit tests pin the exact strings.                                                                                                                                                                                                                                                    |
| D4  | **Two embedders behind one interface:** `gemini` (real) and `mock` (deterministic feature hashing: words → 768 buckets, L2-normalised). Selected by `AI_PROVIDER`; `GEMINI_API_KEY` is required only when `AI_PROVIDER=gemini`. Each document records its `embedding_model` (e.g. `gemini-embedding-2@768`). Searching a workspace with mixed models is refused with a clear error, and `pnpm kb:reembed` fixes it.                                                                                                                                                     | CI and local tests need no network or secret (ADR-0006). The mock still ranks text with shared words higher, so retrieval tests are meaningful and not just "returns something". Storing the model prevents silently comparing incompatible vectors.                                                                                                                                                                                                                                              |
| D5  | **Untrusted PDFs are parsed only in the worker, inside a Node `worker_threads` thread** with a memory cap (`resourceLimits`) and a **30 s hard kill** (`worker.terminate()`). Page count is checked **before** extracting text (> 50 → fail). Library: **`unpdf`** (MIT, PDF.js-based, maintained, ~4M weekly downloads) with an image-size cap.                                                                                                                                                                                                                        | `unpdf` itself warns that for untrusted PDFs, images are unlimited by default, all pages are processed in one call, and parsing runs **on the event loop**, so a `Promise` timeout cannot stop it ([unpdf](https://www.npmjs.com/package/unpdf)). Only killing a thread really stops CPU-bound parsing. The old PDF.js code-execution bug is fixed from 4.2.67 ([GHSA-wgrm-67xf-hhpq](https://github.com/advisories/GHSA-wgrm-67xf-hhpq)); unpdf bundles PDF.js 5–6. This is threat T12.          |
| D6  | **Upload validation follows OWASP's file upload cheat sheet:** an extension allowlist **and** a content check (`%PDF-` signature for PDF; strict UTF-8 with no NUL bytes for `.md`/`.txt`). The browser's `Content-Type` is ignored. The size limit is enforced **while the body streams in**, not after it has been read. The filename is used only as a display title (length-limited, React-escaped). Files are stored as `bytea`, are **never served back**, and the blob is deleted after successful ingestion. Admin+ only, with the existing Origin/CSRF checks. | Each rule maps to a line of the [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html). Never serving files back removes the "public file retrieval" threat class entirely. Threats T11 and T12.                                                                                                                                                                                                                                            |
| D7  | **Cost and abuse caps.** Per workspace: ≤ 100 documents and ≤ 50 MB stored. **≤ 300,000 extracted characters per document** (about 75k tokens), otherwise it fails with "document too long". Upload and test-search **rate limits** use the existing `app_rate_limit` table. SHA-256 dedupe: uploading the same file twice returns **409** with a link to the existing document.                                                                                                                                                                                        | A 5 MB `.txt` file could otherwise become ~2,500 chunks and blow through free-tier embedding quota. This is a refinement of FR-K1; docs/01 is updated to match.                                                                                                                                                                                                                                                                                                                                   |
| D8  | **Chunking:** split along Markdown headings (ignoring `#` inside code fences), then pack paragraphs up to **~500 tokens with ~15% overlap**. Each chunk keeps its `heading_path` ("Billing › Refunds"). Token counts are an **estimate** (characters ÷ 4) stored as `token_estimate`.                                                                                                                                                                                                                                                                                   | Values come from docs/02 §5.2 and are tuned in step 6 by measured recall@5. There's no local Gemini tokenizer; calling the count-tokens API per chunk would waste quota. Naming the column `token_estimate` keeps it honest (docs/02 is updated).                                                                                                                                                                                                                                                 |
| D9  | **Background job:** pg-boss queue `kb.ingest` (ADR-0005), enqueued **in the same transaction** as the document insert. Retries with backoff for _temporary_ errors (embedding 429/5xx/timeout). _Permanent_ errors (bad file, too many pages, no text) mark the document `failed` without retrying. When retries run out, the job goes to a dead-letter queue and the document is marked `failed`. The handler is **idempotent**: it locks the document row and replaces all of its chunks in one transaction. A document deleted mid-job makes the job a no-op.        | NFR-REL2. Retrying a corrupt PDF just wastes time. pg-boss's "one job per key" protection depends on the queue policy, so correctness must not depend on it. pg-boss 12.x needs Node ≥ 22.12 and Postgres ≥ 13 (we have 24 and 17) ([pg-boss](https://www.npmjs.com/package/pg-boss)).                                                                                                                                                                                                            |
| D10 | **Hybrid retrieval:** pgvector top-8 (cosine) **+** full-text top-8, merged with **Reciprocal Rank Fusion, k = 60**, keeping the top 5. Vector search sets `hnsw.iterative_scan = relaxed_order` and re-sorts by distance. Only `ready` documents of the caller's workspace are searched. Each result carries its vector similarity, keyword rank, RRF score and which search(es) found it.                                                                                                                                                                             | RRF is the standard, tuning-free way to merge rankings; k = 60 comes from the original paper ([Cormack et al., SIGIR 2009](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf)). One HNSW index serves all tenants, and filtering happens _after_ the index scan. Without iterative scans, a small workspace could get **fewer than 8 results** ([pgvector §Iterative index scans](https://github.com/pgvector/pgvector)). The vector score is kept for M5's "insufficient knowledge" threshold. |
| D11 | **KB full-text search uses the `english` config** (stemming), unlike tickets (`simple`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Finding #41: `simple` does not match "syncing" to "sync". Help articles are long-form English prose where stemming helps. The synthetic demo is English-only; that limitation is documented.                                                                                                                                                                                                                                                                                                      |
| D12 | **The UI uploads through the REST endpoint** (a small client component that sends `FormData` to `POST /api/v1/kb/documents`), not through a Server Action.                                                                                                                                                                                                                                                                                                                                                                                                              | Server Actions have a small default body limit. Raising it would raise it for **every** action. One validated upload path serves both the UI and the API.                                                                                                                                                                                                                                                                                                                                         |
| D13 | **The worker is its own entrypoint** (`src/worker/index.ts`), bundled with esbuild into the same Docker image and run as a second process (docs/02 §7). Locally: `pnpm worker`. E2E starts web + worker.                                                                                                                                                                                                                                                                                                                                                                | docs/02 already plans a modular monolith with `web` and `worker` processes. Next.js standalone output does not include the worker's dependencies, so a bundle is needed.                                                                                                                                                                                                                                                                                                                          |
| D14 | **Synthetic data only.** The upload page says "demo: do not upload confidential documents". The evaluation corpus is a fictional "Nimbus Cloud Storage" help centre.                                                                                                                                                                                                                                                                                                                                                                                                    | Free-tier Gemini inputs "are used to improve [Google's] products" ([pricing](https://ai.google.dev/gemini-api/docs/pricing)). NFR-PRIV1, T17.                                                                                                                                                                                                                                                                                                                                                     |

## 3. Steps (each one committed with CI green)

1. **Foundations:**
   - New dependencies `pg-boss`, `ai`, `@ai-sdk/google`, `unpdf`, and `esbuild` (dev). Each is checked for licence, maintenance, `pnpm audit`, and **no same-day release**.
   - Env vars `AI_PROVIDER` and `GEMINI_API_KEY`, validated in `env.ts`.
   - Migration `0003`: `kb_document`, `kb_document_blob`, `kb_chunk` (HNSW + GIN indexes), and `ai_usage` (for embedding token usage; M5 adds its budget).
   - Tenant-scoped repository with integration tests.
   - docs/01 and docs/02 updated (D2, D7, D8, D11).
2. **Ingestion core** (pure functions, unit-tested):
   - file validation (magic bytes, UTF-8);
   - text extraction (`.md`/`.txt`; PDF in a sandboxed thread);
   - normalisation and the heading-aware chunker;
   - embedder interface with the mock and Gemini adapters (D3 prefixes, batching, timeout).
   - **Malicious-file fixtures:** renamed binary, `%PDF` polyglot text, 51-page PDF, encrypted PDF, scanned (no text) PDF, truncated PDF, and a slow/hostile PDF that must be **killed at the timeout**.
3. **Jobs and worker:**
   - pg-boss setup and the `kb.ingest` handler, with transactional enqueue;
   - temporary vs permanent failure handling and the dead-letter queue;
   - idempotent re-run; delete-during-ingest race test;
   - worker entrypoint, esbuild bundle, Dockerfile and CI updates;
   - an end-to-end pg-boss integration test (send → worker → `ready`).
4. **Retrieval + REST API:**
   - Hybrid RRF service (D10).
   - Endpoints: `GET/POST /api/v1/kb/documents`, `GET/DELETE /api/v1/kb/documents/{id}`, `POST /api/v1/kb/documents/{id}/retry`, `POST /api/v1/kb/search`.
   - Problem Details, OpenAPI, rate limits, caps and dedupe.
   - **A cross-tenant test for every route**, plus a retrieval test with identical text in two workspaces (only your own is ever returned) and a role-matrix test.
   - Audit events for upload, delete and retry.
5. **Knowledge UI:**
   - document list with status badges (auto-refreshes while anything is pending or processing);
   - upload form with clear errors, delete with confirmation, retry;
   - document page showing its chunks;
   - test-search panel;
   - nav link and overview count;
   - axe scans on desktop and mobile; keyboard pass.
6. **Evaluation and finish:**
   - **Nimbus corpus:** ~35 synthetic help articles (a few also as reproducibly generated PDFs), plus **1 poisoned article** reserved for M5's injection tests.
   - **~80 answerable questions**, each labelled with the article and an **evidence phrase**. A chunk counts as "gold" if it contains the phrase, so labels survive changes to chunk size.
   - `pnpm eval:retrieval` reports **recall@5, MRR@5**, search latency (p50/p95), embedded tokens and estimated cost. It runs in two modes:
     - **mock**, in CI, as a regression guard;
     - **Gemini**, run manually, as the real baseline.
   - **Experiments:**
     - chunk size 300 / 500 / 800 tokens, with and without overlap;
     - vector-only vs keyword-only vs hybrid.
       The results table and chosen settings go to `docs/eval/retrieval-baseline.md`.
   - **You spot-check ~20% of the question labels** (a short checklist).
   - Demo knowledge base seeded into `nimbus-demo`; E2E journey (upload → ready → test search finds it → delete → gone).
   - ADR-0013 (embedding model, dimensions, PDF sandboxing), screenshots, README, milestones.

## 4. Done when

- [x] FR-K1–K4 each covered by named tests (`describe("FR-K2 …")`).
- [x] Ingestion integration tests pass: md, txt and PDF reach `ready`. Every malicious fixture ends `failed` with the right reason, and the hostile PDF is killed within the timeout.
- [x] A job re-run is idempotent (same chunks, no duplicates). Deleting removes chunks immediately, including mid-ingest.
- [x] Cross-tenant test for **every** KB route returns 404. Retrieval never returns another workspace's chunks. Role-matrix tests pass.
- [x] Upload caps, dedupe 409 and rate limits are tested. The browser `Content-Type` is shown to be ignored.
- [ ] **Retrieval baseline recorded** with Gemini (mock baseline and CI guard: done, see `docs/eval/retrieval-baseline.md`; Gemini run pending) (recall@5 and MRR@5 on ~80 questions, plus latency and cost), and the mock baseline is guarded in CI. The target is recall@5 ≥ 90%. If it's missed, the gap and next steps are documented honestly rather than hidden.
- [x] 0 serious/critical axe violations on the knowledge pages (desktop + mobile).
- [x] OpenAPI document updated and validated in CI. The Docker image builds with the worker.
- [ ] CI green.

## 5. Out of scope for M4

- **AI triage, drafts, citations and "source removed" labels (M5).** M4 delivers the deletion side of FR-K3; M5 shows deleted sources in drafts.
- **Prompt-injection evaluation (M5/M6).** M4 only stores the poisoned article and each chunk's provenance.
- **Measuring refusals and calibrating `retrieval_min_score` (M6).** The unanswerable question set itself was added in M4 step 6 (30 questions, finding #73).
- **OCR for scanned PDFs, `.docx`/HTML uploads, and editing documents in the app.**
- **Antivirus scanning or Content Disarm & Reconstruct.** This is recorded as accepted risk **AR-006**, mitigated by text-only extraction in a sandboxed thread and never serving files back.
- **Worker health endpoint and alerting (M8).**
- **Global daily embedding budget for the live demo (M8).** The Gemini free tier allows 1,000 embedded texts per day per project (finding #70), and every search embeds the question; the demo needs a counter that stops embedding calls before the quota and shows a clear "demo limit reached" message.
